## 1. 产品概述

面向上班族的个人健康管理 App。通过手环采集的行为数据（经系统健康中枢聚合），识别久坐等工作期不良行为，结合用户健康标签（如颈椎病），由 LLM 生成个性化提醒文案，在合适的时机推送给用户，引导其进行拉伸活动，并根据用户反馈持续优化提醒策略。

**P0 目标（本档范围）**：打通「手环数据 → 久坐规则触发 → LLM 文案生成 → 通知触达 → 拉伸页 → 反馈回流」最小闭环。

**非目标（P1/P2）**：数据看板与内容库（P1）、通知策略 AI 频控（P1）、AI 对话问诊（P2）、直连 BLE 手环、姿势检测摄像头方案。

## 2. 总体架构

工程架构**完全遵循架构文档**：视图层/领域层/数据层三层，Screen、ViewModel、UseCase、Repository、DataSource 五类架构组件，多 package 模块化（base/feature/domain/core 四类模块），get_it + injectable 依赖注入，Result 模式处理 API 错误响应。本文档只做健康助手业务到该架构的映射。

```
┌────────────────────────── app（壳模块）──────────────────────────┐
│  DI 初始化（injectable 配置生成）、路由注册、通知点击深链分发、启动逻辑  │
└───────────────────────────────────────────────────────────────────┘
   feature_onboarding / feature_home / feature_stretch / feature_profile
        │  ScreenRoute ⇄ Screen ⇄ (Intent/State/Event) ⇄ ViewModel
   feature_design_system（主题 token 落地 + 通用组件）
        │
   domain_all（UseCase：规则评估 / 文案获取 / 反馈记录 / 降频计算…）
        │
   core_health / core_reminder / core_profile（Repository + DataSource）
        │
   core_network（advice 接口 + Result 封装）  core_database（drift）
        │
   core_model（业务对象）  base_utils  base_lints  snapshot_test
```

关键原则（沿用 v0.1，与架构文档不冲突）：

1. **手环数据只从系统健康中枢读**（HealthKit / Health Connect），不直连 BLE、不接厂商私有 SDK。P0 先用社区 `health` 插件验证链路，自研桥接插件作为替换项（见 §6.1），替换发生在 DataSource 实现层，Repository 接口不变。
2. **规则引擎在本地、领域层**：久坐判断这类确定性逻辑不依赖网络和 LLM，以 UseCase 组织。
3. **LLM 只做文案**：云端收到触发上下文后生成个性化文案并下发，客户端缓存最近 N 条备选文案以应对网络失败。
4. **画像与反馈沉淀在云端**：为 P2 对话助手预埋上下文数据。

## 3. 工程结构与模块划分

### 3.1 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 模块化 | Melos 管理多 package | 遵循架构文档的 base/feature/domain/core 四类模块 |
| 依赖注入 | get_it + injectable | 注解规范见架构文档 3.1 |
| 状态管理 | ViewModel 持有 State（架构文档 3.2 的 ScreenRoute/Screen/ViewModel/State/Intent/Event 套路） | 不引入 Riverpod/Bloc（v0.1 方案作废） |
| 健康数据（初期） | 社区插件 `health` | 双端统一 API，先跑通链路 |
| 健康数据（替换） | 自研 `health_bridge` 插件 | 需要后台推送订阅时替换，见 §6.1 |
| 本地通知 | `flutter_local_notifications` | P0 直接使用 |
| 本地持久化 | drift (SQLite)，经 core_database 封装 | 触发记录、反馈事件、规则状态 |
| 网络 | dio，经 core_network 封装 + Result 模式 | |
| 云端 | 任意轻量后端（Node/Go）+ Postgres | P0 仅两个接口 |
| LLM | 云端代理调 LLM API（模型可替换） | 客户端不直连 LLM |

### 3.2 模块清单（健康助手业务映射）

| 模块 | 类型 | 职责 |
|---|---|---|
| `app` | 壳 | 入口、DI 配置聚合、路由表、通知深链（`healthassistant://stretch?advice_id=`）分发 |
| `feature_onboarding` | feature | 首启三屏（价值页/健康标签/权限引导），对应设计稿 01–03 |
| `feature_home` | feature | 今日页（计数卡/数据源状态/下次预估），设计稿 04 |
| `feature_stretch` | feature | 拉伸页 + 动作详情（深链落地页），设计稿 05–06 |
| `feature_profile` | feature | 我的 + 提醒设置，设计稿 07–08 |
| `feature_design_system` | feature（通用） | ThemeData（《设计规范.md》翻译）、通用组件：胶囊 chip、卡片、反馈按钮组、空态组件 |
| `domain_all` | domain | 全部 UseCase（见 §5） |
| `core_health` | core | HealthRepository / HealthDataSource：活动分段与久坐标记的读取、后台数据变化订阅 |
| `core_reminder` | core | ReminderRepository：规则配置存取、触发状态（久坐累计/上次提醒时间）、advice 日志、反馈事件 |
| `core_profile` | core | ProfileRepository：健康标签、静音时段、频控参数的本地缓存与云端同步 |
| `core_network` | core（支撑） | dio 封装、advice/profile 接口定义、Result 模式 |
| `core_database` | core（支撑） | drift 库创建升级、表结构（reminder_log / feedback_event / rule_state） |
| `core_model` | core（支撑） | 纯业务对象，见 §4；不含任何业务代码 |
| `base_utils` | base | 日志、时间处理（时区/工作时段判定工具）等 |
| `base_lints` | base | 静态检查规则统一管理 |
| `snapshot_test` | 测试 | 快照测试（按架构文档 2.2.8 单独成模块，避免字体进主工程） |

模块划分遵循架构文档 2.1 的"讲故事"原则：如「久坐累计状态属于提醒域还是健康数据域」——累计状态是规则引擎的中间产物而非采集事实，故放 `core_reminder` 而非 `core_health`。

### 3.3 视图层编码套路（遵循架构文档 3.2）

每个 Screen 的代码组织为：`ScreenRoute`（跳转入口与中间件）/ `Screen`（纯 UI，经 onIntent 上抛事件）/ `ViewModel`（持有 State，对接 UseCase）/ `State`（不可变视图数据类）/ `Intent`（用户事件）/ `Event`（下层一次性事件，如"文案生成完成"）。

以拉伸页为例的 Intent/Event 清单：

- Intent：`LoadAdvice(adviceId)`、`CompleteAction(actionId)`、`FeedbackSelected(FeedbackAction)`、`SkipAction(actionId)`
- Event：`AdviceReady(advice)`、`AdviceFallbackUsed(staticText)`、`FeedbackAccepted`

## 4. 数据模型（core_model）

与 v0.1 一致，仅调整归属：全部实体定义在 `core_model`，供各层转换使用。

```dart
/// 一段连续行为（来源：健康中枢的活动分段/久坐标记）
class ActivitySegment {
  final String id;              // 平台数据源 + 原始 ID 拼接，保证幂等
  final ActivityType type;      // sedentary / stationary / walking / running ...
  final DateTime start;
  final DateTime end;
  final String source;          // healthkit / health_connect
}

/// 用户健康标签
class HealthTag {
  final String code;            // cervical_spondylosis / lumbar_strain / eye_strain / none
  final List<String> subCodes;  // 预留：严重程度等
}

enum FeedbackAction { done, snooze, stopToday, neverAgain }

class FeedbackEvent {
  final String adviceId;
  final FeedbackAction action;
  final DateTime at;
  final String triggerContextJson;
}

class TriggerContext {
  final List<String> healthTags;
  final int continuousSedentaryMinutes;
  final TimeBand timeBand;
  final int recentFeedbackDone7d;
  final int recentFeedbackRejected7d;
  final String locale;
}
```

云端 Profile / advice_log 表结构与 v0.1 相同（PRD §4.2）。

## 5. 领域层设计（domain_all）

UseCase 遵循架构文档 3.3：只含一个 `call` 函数、依赖全部走构造函数注入、统一 `@injectable` 注解（工厂模式）。

| UseCase | 职责 | 依赖 |
|---|---|---|
| `FetchSegmentsUseCase` | 拉取时间窗内活动分段（冷启动补拉 12h） | HealthRepository |
| `EvaluateSedentaryUseCase` | **规则引擎核心**：输入分段流 + 规则，输出 TriggerEvent（含静音时段/冷却/活动打断判定） | ReminderRepository（读规则与状态）、base_utils 时间工具 |
| `GenerateAdviceUseCase` | 触发后取文案：调云端 advice，3s 超时降级静态兜底，同上下文指纹 24h 命中缓存 | AdviceApi（core_network）、ReminderRepository |
| `ScheduleReminderUseCase` | 文案就绪后经 local_notifier 发通知（深链携带 advice_id） | 通知服务 |
| `RecordFeedbackUseCase` | 反馈落库（本地优先）+ 上报云端 | ReminderRepository、ProfileRepository |
| `AdjustFrequencyUseCase` | 简化频控：近 7 天负面占比 > 50% → 放宽阈值/冷却 | ReminderRepository |

规则判定逻辑（EvaluateSedentaryUseCase 内，与 v0.1 一致）：

```
onSegmentArrived(seg):
  if seg 是久坐/静止 且 处于 activeBand + activeDays: currentStreak += seg.duration
  else if seg 是 walking/running: currentStreak = 0
  if currentStreak >= threshold 且 距上次提醒 >= cooldown:
      currentStreak = 0; emit TriggerEvent(context)
```

## 6. 数据层设计

### 6.1 core_health：HealthRepository（接口不变，实现可替换）

```dart
abstract class HealthRepository {
  Future<bool> requestPermissions(Set<HealthDataType> types);
  Future<bool> hasPermissions(Set<HealthDataType> types);
  Future<List<ActivitySegment>> fetchSegments(DateTime from, DateTime to);
  Stream<HealthUpdateEvent> get onBackgroundUpdate; // 自研插件阶段启用
}
```

- `HealthDataSourceImpl（community）`：P0 前四周，包装社区 `health` 插件。
- `HealthDataSourceImpl（bridge）`：W5 起替换，包装自研 `health_bridge` 插件（HealthKit `HKObserverQuery` + background delivery；Health Connect `PassiveMonitoringClient`）。
- DataSource 双实现并存期间经 injectable 的可配置注册切换；HealthRepository 及其上层无感。
- 双端差异（iOS 引导授权苹果健康 / Android 引导安装 Health Connect）封装在 DataSource 内。

### 6.2 core_reminder / core_profile

- `ReminderRepository`：暴露规则配置 CRUD、触发状态读写、advice 日志追加、反馈事件查询（7 天窗口统计）。实现经 drift（core_database）。
- `ProfileRepository`：标签与偏好本地缓存 + 云端 profile 同步（失败静默重试，本地优先）。
- 注解规范（遵循架构文档 3.4）：`@LazySingleton(as: HealthRepository)` 标注 `HealthRepositoryImpl` 等，DataSource 同理默认单例。

### 6.3 core_network 与 Result 模式（遵循架构文档 3.5）

advice 接口返回 `Result<AdviceResponse>`，调用侧 switch 匹配处理：

```dart
sealed class Result<T> { ... }  // Success<T> / Failure<T>（错误码、可重试标记、兜底文案键）

// GenerateAdviceUseCase 内
final result = await _adviceApi.post(context).timeout(3s);
switch (result) {
  case Success(:final data): return data;
  case Failure(): return Advice.fallback(context.healthTags); // 静态兜底
}
```

Prompt 安全红线与 v0.1 一致（≤60 字、禁诊断/用药表述、结构化输出 `{text, action_hint}`、失败兜底），详见 PRD §5.3 引用。

## 7. 关键链路时序（后台唤醒触发，v0.1 逻辑 + 组件标注）

```
手环同步 → 系统健康中枢更新
  → [iOS] HKObserverQuery / [Android] PassiveMonitoring 回调（health_bridge 插件）
  → DataSource → HealthRepository.onBackgroundUpdate
  → EvaluateSedentaryUseCase（静音时段/冷却检查）
  → GenerateAdviceUseCase（Result，失败走静态兜底）
  → ScheduleReminderUseCase → 通知（深链 advice_id）
  → 用户点击 → app 路由分发 → feature_stretch ScreenRoute → 反馈 Intent
  → RecordFeedbackUseCase（本地即时生效 + 上报）
```

前台兜底：App 冷启动时 `FetchSegmentsUseCase` 补拉近 12h 分段重跑规则（按触发窗口幂等去重）。

## 10. 风险与开放问题

v0.1 风险表全部保留（Health Connect 国内 ROM 覆盖、iOS 后台唤醒、同步延迟、LLM 成本、通知关闭、合规），另新增：

| 风险 | 应对 |
|---|---|
| 多 package 工程对单人开发的维护成本 | 模块数已按 P0 最小集裁剪（16 个）；后续功能默认进既有模块，不轻易新建 |
| ViewModel 基类/代码模板缺失（架构文档提及"模板一键生成"但未提供） | W1 脚手架阶段手写一个 feature 作为参照模板（feature_onboarding 最简，先行） |
| injectable 生成配置与后台隔离场景 | 后台回调入口（health_bridge 唤醒）不依赖 UI 上下文，仅经 GetIt 取 UseCase 执行 |
